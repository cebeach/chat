# Refactoring plan: readability and extensibility (revision 2)

## Context
`chat.py` is 2073 lines (about 40% of the roughly 5,000 non-test lines). It holds startup config, file includes, project/`/remember` logic, ~750 lines of `/duel` orchestration, a 207-line `if/elif` `handle_command`, and a 143-line `main`. Adding a slash command means editing four places by hand: the handler branch, `COMMANDS` (`ui.py:21`), `print_help` (`ui.py:65`) and the completer (`ui.py:573`). These have already drifted: the help table lists `/help` (`ui.py:81`) but the handler matches `/?` (`chat.py:1701`).

Goal: make new commands a one-place change and shrink `chat.py`. Every step is behavior-preserving except one deliberate, labelled fix (the `/help` mismatch, in step 2); step 1's `/system` fallback collapse is also a removal of code believed dead, pinned by a test. Small, independently mergeable steps, ordered by dependency first (step 2 needs step 1) and then by value; steps 3 and 4a do not depend on 1 or 2, and 4b needs 4a. Each depends only on steps already merged.

Line numbers are verified as of `main` at commit 67e3381. **Line numbers go stale:** step 1 rewrites `handle_command` and step 2 changes it again. Each step re-derives its ranges (`grep -n "^def \|^class "`) when picked up and treats the numbers here as hints.

## Delivery
One PR per step, one branch per step, never on `main` (main only receives squash-merged PRs):

| Step | Branch |
|---|---|
| 1 | `refactor-command-handlers` |
| 2 | `refactor-command-registry` |
| 3 | `refactor-includes-module` |
| 4a | `refactor-duel-host` |
| 3b | `refactor-includes-imports` |
| 4b | `refactor-duel-module` |
| 5 | one branch per sub-item, named when that step is picked up |

**Why a branch per step:** a direct commit to `main` would bypass review; one long branch would put ~2000 lines of moves in one diff and let a failing late step block the early, low-risk ones. A branch per step keeps each diff reviewable, each gate result attributable, and each step revertable.

For each step: `git switch main && git pull`, then `git switch -c <name>`. Check `git branch --show-current` before each commit. Commit only the relevant files by name (leave every untracked `*-plan.md` file alone, including the plan files themselves). Approving a step authorizes local commits on its branch only (each message ends with the `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` trailer). Pushing and opening the PR are outward-facing and not covered; after the gate passes I stop and ask permission to push and `gh pr create`. The user merges. Only after they confirm the merge do I update `main` and branch the next step. I never branch from an unmerged branch.

The plan files are working notes: no step edits them and none keeps a progress log.

## Gate (after every step, before the next)
- `venv/bin/ruff check . && venv/bin/ruff format --check .`
- `venv/bin/python -m pytest -m "not integration"`

If anything fails it is fixed within the same step. No manual smoke test and no running llama-server are needed anywhere in this plan.

Accepted risk: the gate excludes the `integration` tests, including the `llama_parallel(2)` `/duel` ones, so steps 4a and 4b are verified only against the offline fakes (`run_session()`, `SlotScript`, `test_duel_phase.py`). If a llama-server with `--parallel 2` is available, the user may run `--llama-model qwen35-2B-Q8_0-parallel2` on those PRs; it is optional and not part of the gate.

## Steps

1. **Pin and extract handlers** (low risk). Pin first, then refactor, in the same PR:
   - Enumerate every branch of `handle_command` (18) and audit which already have a test driving them through `handle_command` or `run_session()` (`tests/helpers.py`). `/recall` has no handler test (only `Conversation.recall` is tested) and `/cat` is only mentioned in a display test. Add tests for every unpinned command or branch (including each `FileNotFoundError` and usage-error path), and run them green against the current code before touching it.
   - Fix one handler contract: `_handle_<name>(args, client, conversation, state) -> bool`, the bool being `handle_command`'s existing "REPL should continue" result (`/exit` returns False). Extract the 13 inline bodies: short `/?`, `/exit`, `/clear`, `/conversations`, `/stats`; long `/system`, `/save`, `/load`, `/cat`, `/recall`, `/retry`, `/read`, `/info`. The five that already delegate (`/set`, `/duel`, `/config`, `/project`, `/remember`) are left alone here and adapted in step 2. Add `_load_named` for the usage-check / `_conversations_dir` / `Conversation.load` / `FileNotFoundError` shape in `/load` and `/cat`; the two commands differ in usage text and failure text, so those are parameters, and the apply step runs inside the same `try` as the load so its failures are still reported as before.
   - `/system` has a three-layer fallback for the cwd check: a `try` using `is_relative_to`, an `except AttributeError` branch repeating it behind `hasattr`, and a parent-walk fallback. `config.py:10` imports `tomllib`, so the project already requires Python 3.11+; all of the fallback is dead code. Collapse it to `in_cwd = resolved_path.is_relative_to(cwd)` in this step (`resolved_path.is_file()` already excludes the `== cwd` case the parent walk allowed; tests covering a path inside and outside the cwd pin it).
2. **Command registry** (high value). New `commands.py` with a frozen `Command(name, aliases, usage, help, handler_name, complete)`. `handler_name` is the name of the `_handle_*` function as a string, written in the table itself (never a function object); `complete` is plain data (`None`, `"conversation"`, `"project"`, or a tuple of fixed subcommands), not a callable. There is one mechanism for naming handlers: the table. There is no separate name map and nothing is bound or mutated after import.
   - Derive `COMMANDS`, `print_help` and the completer's argument cases (`/load`, `/cat`, `/project` subcommands) from the table. `ui.py` maps each completion kind to candidates, keeping `commands.py` free of `Conversation` and `list_projects`.
   - Existing helpers (`_handle_set`, `_handle_config`, `_handle_project`, `_handle_remember`, `_handle_duel`) get thin adapters with the step 1 contract rather than signature changes, so their tests are untouched.
   - `handle_command` becomes a lookup with the same signature `(cmd, args, client, conversation, state)`.
   - Import direction: `commands.py` imports neither `chat.py` nor `ui.py`; `ui.py` imports `commands.py`. `commands.check_handlers(namespace)` takes `chat`'s namespace as an argument (it imports nothing from `chat`) and raises if any `handler_name` is missing from it; `chat.py` calls it once at import time, so a typo fails at startup. A test asserts the same.
   - **Resolve names at dispatch.** `handle_command` looks up `globals()[handler_name]` on each call, never storing the function, so `mock.patch.object(chat, "_handle_x", ...)` still takes effect (no test patches any `chat._handle_*` today).
   - **The one deliberate behavior change:** `/help` and `/?` both work (alias); `COMMANDS` now also offers `/help`. Update `docs/commands.md` and `README.md`.
   - New tests: every registry command appears in `COMMANDS`, help output and the dispatcher; `/help` and `/?` both reach help. Test completion as a unit: call `init_readline`, fetch the completer with `readline.get_completer()`, patch `readline.get_line_buffer`, and assert candidates for `/lo`, `/load `, `/cat `, `/project ` and `/project use `. A PTY test (`tests/pty_helpers.py`) is optional and only if it is cheap and not timing-sensitive. Existing tests touching `COMMANDS`/`print_help` (`test_served_model.py:106-108`, `test_duel_display.py:63-64`, `test_conversation_save.py:222`) only check membership and should pass unchanged.
3. **`includes.py`**: move `_read_file`, `_READ_FILE_MAX_BYTES`, the include regexes and newline helpers, `build_message`, `expand_includes` (currently `chat.py:~227-375`, starting at the comment above `_READ_FILE_MAX_BYTES`). `_prepare_user_message` stays in `chat.py` because tests patch `chat.display_error` (e.g. `tests/test_turn_echo.py:178`). `chat.py` re-exports the moved names (temporary) so `tests/test_includes.py:11` and the `/system` and `/read` uses keep working. The one test edit in this step: `tests/test_includes.py:125` retargets `monkeypatch.setattr(chat, "_READ_FILE_MAX_BYTES", 1024)` to `includes`. Re-verify when picking the step up: grep `tests/` for `monkeypatch.setattr(chat, ...)` / `patch(...chat...)` on every moved name (a review-time grep found none besides line 125), and confirm the moved range makes no `display_*`/`console` calls (none at review time). Note that after step 1 `/system` tests patch `chat._read_file` (`tests/test_commands.py`); retarget that patch too.
   - **3b (closing the re-export):** after 3 merges, a follow-up (its own small PR `refactor-includes-imports`) removes the re-exports: `chat.py` imports only the names it uses, and `tests/test_includes.py:11` imports from `includes`. If the user prefers to keep the re-exports permanently, that is their call and 3b is dropped.
4. **Duel move** (medium risk; two PRs).
   - **The problem:** the duel block (`chat.py` ~941-1698, 30 top-level defs/classes including `_Job` and `_Turn`) calls helpers defined elsewhere in `chat.py`: `_auto_save`, `_conversations_dir`, `_fits_window`, `_initial_duel`, `_prepare_user_message`, `_reply_model`, `_sync_notes`, `_sync_server_info`, `_update_think_tags`, `_validated`. A `duel_session.py` doing `from chat import ...` is circular, and `import chat` is worse: `python chat.py` runs as `__main__`, so it would load a second copy with its own `State`.
   - **Why not move the helpers:** five of them print, and tests patch `chat.display_error`, `chat.display_info` and `chat.console.print` (e.g. `run_session` in `tests/test_turn_echo.py`, `tests/test_conversation_save.py:185`) while running `main()`; moved helpers would bypass those patches. The same applies to the block's own UI calls, patched on `chat` by `run_session()` (`tests/test_turn_echo.py:82`).
   - **The host has three groups, not two:** (a) the ten helpers above; (b) the UI functions `display_error`, `display_info`, `display_ledger`, `display_stats`, `display_assistant_stream`, `echo_suppressed`, `get_multiline_input`; (c) **`console`**, which the block uses 12 times (e.g. `console.print()` and `console.print(diff, markup=False, highlight=False)`) and which `tests/test_turn_echo.py:158,182` patches as `chat.console.print`. Because that patch replaces an attribute of the shared `ui.console` object, a moved block importing `console` from `ui` sees it too; but to keep the rule uniform ("the duel code reaches `chat`-level names only through the host") `console` is a `DuelHost` member. `_show_text` (5 uses, all inside the block, defined at ~1354) moves with the block and is not a host member.
   - **First action of 4a:** re-read the block and re-verify all three lists (counts come from this review's grep and may have drifted). Checked: the block never references `State` (it only receives `state`), and mentions `Conversation` only in annotations/comments (sides are built with `duel.new_conversation`). If the re-read finds otherwise, add it to the host.
   - **4a (in place, no file moves):** add a frozen `DuelHost` dataclass holding the ten helpers, the seven UI functions and `console`, and `chat._duel_host()` building it per call with each callable member looking the name up in `chat`'s globals at call time (e.g. `fits_window=lambda *a, **k: _fits_window(*a, **k)`; `console` via a small object or property resolving `chat.console` at access time), so `mock.patch.object(chat, ...)` still works. Thread it through `_handle_duel` into every duel function using those names. `host` is an optional trailing parameter defaulting to `None`, resolved to `_duel_host()` inside the function (not as a def-time default), so `tests/test_duel_phase.py` calls keep their signature. No existing test changes. **This default is temporary and works only while the code lives in `chat.py`;** step 4b removes it (see there).
   - **4a adds one new test:** for every `DuelHost` member (ten helpers, seven UI functions, `console`), patch the matching name on `chat` and assert the host uses the patched version.
   - **`_handle_duel` stays in `chat.py`** as the host-building entry point, so step 2's adapter keeps pointing at a `chat.py` function and `duel_session.py` has no entry point that needs `chat`.
   - **4b, `duel_session.py`:** move the duel functions and classes (including `_Job`, `_Turn` and `_show_text`) except `_handle_duel`, together with the block's module-level state: `_DUEL_SLOTS` (~1187), `_DUEL_KEYS` (~1192, used by `_duel_set`, `_start_duel` and the usage text) and `_duel_rng` (~1190). Split `_run_phase` (~139 lines). It imports `duel.py`, `llama_client`, `tokens`, `conversation`, never `chat`, and receives helpers/UI/console via the host. Keep `duel.py` pure. **`host` becomes a required parameter** on every moved function that takes it: `duel_session.py` cannot call `chat._duel_host()`, so the `None` default from 4a is dropped, and `_handle_duel` (still in `chat.py`) builds the host and passes it down. Find every caller with `grep -rn` over `chat.py` and `tests/` (not only `_run_phase` in `test_duel_phase.py`) and update each. Grep `tests/` for `chat._DUEL_` as well and retarget any hit.
5. **Optional, later, each its own PR, each starting with the same audit-and-pin as step 1:** (5a) split `main` into read-turn / send-turn helpers; (5b) project switching and `/remember` into `project_session.py`; (5c) startup validation (`_validated`, `_initial_options`, `_OPTION_KEYS`, `_OPTION_RULES`, `_initial_duel`) into `config.py` (`chat.py` keeps importing them for tests); (5d) readline/tty code out of `ui.py`. Skip splitting `State`. **Interaction with 4a/4b:** `_validated`, `_initial_duel` (5c) and `_sync_notes` (5b) are `DuelHost` members. When one moves, `chat.py` must keep importing the name (the host looks it up in `chat`'s globals), the 4a host test must still pass, and any test that patches `chat.<name>` to influence a caller now living in the new module must be retargeted. Check this per sub-item. Step 5 items are deferred and each needs an explicit go-ahead.
